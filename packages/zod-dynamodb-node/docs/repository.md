# Repository

[日本語](repository.ja.md)

## Role

The backend Repository (`@zodapp/zod-dynamodb-node`) is the core of type-safe operations on DynamoDB, whether or not the Express middleware or the Realtime Gateway is used. It is responsible for:

- Getting Items
- Creating Items
- Partial updates of Items
- Running named mutations
- Deleting Items
- Running named queries
- Running named searches (vector search)
- Data conversion (injecting keys, merging, building and decoding physical keys, converting to and from DynamoDB attribute values)
- Zod validation of input and output
- Applying DynamoDB-specific operation constraints
- Generating change events ([Generating change events](../../zod-dynamodb/docs/realtime.md))

## Usage

```ts
import { createRepository } from
  "@zodapp/zod-dynamodb-node";

// Built from the table definitions and the server-only overrides ([Shared definitions and server-only overrides](../../zod-dynamodb/docs/shared-definitions.md))
const repository = createRepository({
  tables: { tasks, rows },
  overrides, // a list of override()
  vectors: { rows: { content: { slot: ..., filters: ... } } }, // runtime vector settings ([Vector search](vector-search.md))
  dynamodb,
});
```

The other options are:

| Option                         | Content                                                                                                                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `tableNames`                   | Maps the physical layout names to the actual table names (per-environment prefixes, etc.)                                             |
| `cursorSecret`                 | The secret used to sign page tokens                                                                                                   |
| `listener` / `onListenerError` | The receiver of changes ([Generating change events](../../zod-dynamodb/docs/realtime.md)) and errors raised there (logged by default) |
| `resolveVectorConfig`          | A function that looks up the runtime settings of vector search ([Vector search](vector-search.md))                                    |
| `maxRetries`                   | The retry limit for `version` mismatches (5 by default. [Writes](writes.md))                                                          |
| `invalidItems`                 | What to do when stored data cannot be parsed with the item schema ([Named queries](queries.md))                                       |

Example operations:

```ts
const task = await repository.tasks.get({
  workspaceId: "ws1",
  taskId: "task1",
});
// task: { workspaceId, taskId, kind, title, status, ..., createdAt, updatedAt } | null

await repository.tasks.create(
  { workspaceId: "ws1", taskId: "task1" },
  {
    kind: "todo",
    title: "Design",
    status: "todo",
    assignee: null,
    priority: 3,
  },
);

await repository.tasks.update(
  { workspaceId: "ws1", taskId: "task1" },
  { status: "done" },
);
```

Named operations ([Named queries](queries.md), [Writes](writes.md), [Vector search](vector-search.md)) are run by passing the operation to an accessor (`repository.tasks.mutate(taskOps.setStatus, key, params)`). To run a registry operation through validation and authorization (`authorize`, including overrides), use `repository.execute(op, request, { context })`. For operations with `authorize`, `context` is required, and omitting it is a `MissingContextError`. The server API that is called in the same shape as the browser (`createServerApi`) is described in [Server API](server-api.md).

Transactions and batch writes ([Writes](writes.md), [Vector search](vector-search.md)) are not put in the registry; they are used as features of the Repository.

Only item objects are read and written. Physical keys, the entity name, and `version` never appear.

The key on creation is passed as the first argument. The key is not removed from the item schema; the library injects the key from the argument.

When the library or the application generates the key (a random ID, etc.), it is generated by a hook (`generateKey`). Like `onCreate`, `generateKey` is written in the table definition. Instead of deriving a type without the generated key, it receives the values needed for generation (the Partition Key, etc.) as arguments with a schema (`args`). Because there is a schema, calls from the browser can also be validated before sending. The hook also receives the validated create input. Creation is done with `createWithGeneratedKey(args, input)`, separate from `create(key, input)`. To expose it, make it an operation with `o.createWithGeneratedKey()`.

```ts
generateKey: {
  args: z.object({ workspaceId: z.string() }),
  key: ({ workspaceId }) => ({ workspaceId, taskId: crypto.randomUUID() }),
},
```
